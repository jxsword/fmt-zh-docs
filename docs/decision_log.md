## DR-001 2026-11-18 多版本管理策略 [状态: 生效]

- **背景**: fmt.dev 提供多个版本文档（1.0~12.2+），中文站需支持版本切换和历史版本回溯
- **选项与权衡**:
  - 方案A: 仅维护 latest 单版本（优点：简单；缺点：无法查看旧版本，用户体验差）弃用
  - 方案B: 所有版本全量部署（优点：完整；缺点：存储大、维护成本高）弃用
  - 方案C: 保留最近 3 minor + 1 LTS，使用 mkdocs-material + mike 版本切换（优点：平衡存储与可用性，支持版本选择器；缺点：需配置 mike）← **选中**
- **结论**: 采用方案C，部署结构为 `/latest/`、`/12.2/`、`/11.2/` 等子路径
- **理由**: mike 插件原生支持版本管理和别名，GitHub Pages 部署友好
- **影响**: mkdocs.yml 配置、deploy.yml 工作流、站点导航

## DR-002 2026-11-18 段落切分粒度 [状态: 生效]

- **背景**: 增量翻译需对比中英文段落，需定义"段落"的切分规则
- **选项与权衡**:
  - 方案A: 按空行切分（优点：简单；缺点：破坏代码块/表格/列表结构）弃用
  - 方案B: 按 Markdown AST 语义切分，代码块/表格/列表/标题组独立为段（优点：结构完整；缺点：实现稍复杂）← **选中**
  - 方案C: 句子级切分（优点：粒度细；缺点：上下文丢失，翻译质量差）弃用
- **结论**: 采用方案B，段落 ID 格式：`{file}-{type}-{index}`（如 `api-md-code-3`）
- **理由**: 保持 Markdown 结构完整性，避免代码块被误翻译
- **影响**: sync_docs.py、segment_markdown.py、.translation-state.json 结构

## DR-003 2026-11-18 术语表上下文消歇 [状态: 生效]

- **背景**: 同一英文词在不同上下文需不同译名（如 "format" 动词/名词）
- **选项与权衡**:
  - 方案A: 单一译名，人工根据上下文调整（优点：简单；缺点：易不一致）弃用
  - 方案B: 正则上下文匹配 + 默认兜底（优点：自动化程度高；缺点：正则维护成本）← **选中**
  - 方案C: LLM 根据上下文自动消歇（优点：智能；缺点：成本高、不可控）弃用
- **结论**: 术语表增加 `contexts` 字段，支持正则模式匹配上下文窗口
- **理由**: 平衡自动化与准确性，正则规则可版本化维护
- **影响**: config/glossary.yml 结构、translate_batch.py 提示词构建

## DR-004 2026-11-18 代码保护机制 [状态: 生效]

- **背景**: 翻译时必须保护代码块、内联代码、HTML、链接不被翻译
- **选项与权衡**:
  - 方案A: 正则占位符替换法（优点：实现简单、通用；缺点：嵌套结构处理复杂）← **选中**
  - 方案B: Markdown AST 遍历保护（优点：结构化；缺点：依赖特定解析器）弃用
  - 方案C: LLM 指令保护（优点：无需预处理；缺点：不可靠，易漏译）弃用
- **结论**: 使用 `{{PROTECTED_<TYPE>_<HASH>}}` 占位符格式，翻译前替换、翻译后还原
- **理由**: 实现简单、不依赖特定库、支持所有保护类型
- **影响**: protect_untranslatable.py、translate_batch.py、validate_translation.py

## DR-005 2026-11-18 双语对照模式 [状态: 生效]

- **背景**: 用户需要对照原文，便于学习和验证翻译
- **选项与权衡**:
  - 方案A: 侧栏切换（优点：体验好；缺点：移动端受限，需复杂布局）弃用
  - 方案B: 段落悬浮提示 + 独立对照页面（优点：全平台、实现相对简单）← **选中**
  - 方案C: 行内标注（优点：无需交互；缺点：视觉干扰大）弃用
- **结论**: 默认启用段落悬浮显示原文，提供 `?bilingual=true` 独立对照页面
- **理由**: 悬浮提示不干扰阅读，对照页面适合审校和打印
- **影响**: mkdocs.yml 配置、bilingual-toggle.js、bilingual.css

## DR-006 2026-11-18 翻译记忆复用 [状态: 生效]

- **背景**: 相似段落重复翻译浪费成本，需复用历史翻译
- **选项与权衡**:
  - 方案A: 精确 hash 匹配（优点：100%准确；缺点：仅完全相同可复用）弃用
  - 方案B: 语义相似度匹配 + 质量阈值（优点：复用率高；缺点：需向量模型）← **选中**
  - 方案C: 不复用，每次全量翻译（优点：简单；缺点：成本高）弃用
- **结论**: 使用 SQLite + sentence-transformers，相似度 >0.95 直接复用，0.85-0.95 作为 few-shot 示例
- **理由**: 显著降低 LLM 成本，提高术语一致性
- **影响**: translation_memory.py、translate_batch.py、.tm.sqlite

## DR-007 2026-11-18 上游 Breaking Change 分级响应 [状态: 生效]

- **背景**: fmt 可能发布大版本重构文档结构，需应对预案
- **选项与权衡**:
  - 方案A: 无预案，遇到再处理（优点：简单；缺点：被动，风险高）弃用
  - 方案B: 分级响应 L1 自动/L2 半自动/L3 冻结冲刺（优点：有序应对；缺点：需预先定义）← **选中**
  - 方案C: 完全人工处理（优点：灵活；缺点：效率低）弃用
- **结论**: 
  - L1 (结构变化<10%): 自动 hash 匹配迁移
  - L2 (10-30%): 半自动映射建议 + 人工确认
  - L3 (>30%): 冻结翻译 3 个月并行维护旧版，组织翻译冲刺
- **理由**: 降低大版本升级风险，保证用户可用性
- **影响**: 监控告警规则、迁移脚本、社区沟通机制

## DR-008 2026-11-18 社区反馈 SLA [状态: 生效]

- **背景**: 用户报告翻译错误需及时响应和修复
- **选项与权衡**:
  - 方案A: 无 SLA，有空处理（优点：无压力；缺点：用户体验差）弃用
  - 方案B: 分级 SLA（优点：明确承诺；缺点：需资源保障）← **选中**
  - 方案C: 所有 Issue 24h 内解决（优点：响应快；缺点：不现实）弃用
- **结论**: 
  - 关键错误(代码/结构): 24h 内修复部署
  - 术语错误: 48h 内修复 + 同步术语表
  - 一般语言问题: 1 周内合并下一批次
  - 首次响应: 2 个工作日内
- **理由**: 平衡用户体验与维护成本
- **影响**: Issue 模板、监控告警、自动化修复流程

## DR-011 2026-11-19 sync_docs.py 死循环修复与 memgate 内存闸纪律 [状态: 生效]

- **背景**: 2026-11-18 23:25 M1 期间运行 sync_docs.py --init，segment_md 段落分支遇跨行 HTML 注释（行以 < 开头且同行无 >）死循环，2 分 36 秒内存达 12.4GB，触发内核 OOM，整机僵死且 ZCode 被连带退出
- **选项与权衡**:
  - 方案A: 仅加护栏 `if i == start: i += 1`（最小改动；缺点：跨行注释仍被切成空段、丢内容）弃用
  - 方案B: 护栏 + html 分支放宽为 `st.startswith('<')`（跨行注释整块捕获，双保险）← **选中**
- **结论**: scripts/sync_docs.py 两处修复并已离线验证（5 文件 1117 段无死循环）；本机新增 memgate（~/.local/bin/memgate，cgroup 内存上限包裹器），本项目会话内运行长任务脚本一律经 memgate 包裹；另已安装 earlyoom 做系统级前置保护
- **理由**: 护栏杜绝死循环，内存闸保证未知 bug 只损失被限进程而非整机
- **影响**: scripts/sync_docs.py；docs/incident-2026-11-18-oom.md；会话内 Bash 用法；~/.zcode/AGENTS.md（全局纪律）
